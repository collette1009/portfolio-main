About

반복 VOC를 고객 여정의 막힘으로 보고,
응답 시나리오와 자동응대 운영 기준으로 연결하는 사람

CX는 고객 접점에서 발견한 문제를 문의 의도·응답 기준·시나리오·운영 정책으로 바꾸는 일이라고 생각합니다. 고객에게 보이는 답변만 바꾸는 일이 아니라, 그 답변이 어떤 기준으로 만들어지고, 어떤 상황별 시나리오로 분기되며, 어떤 운영 정책으로 유지되는지까지 설계하는 일이라고 봅니다.

저는 반복 문의를 단순 응대로 끝내지 않고, 고객이 배송·환불·교환·제휴 정책 단계에서 어느 시점에 오인하는지, 그 문의가 다시 반복되지 않으려면 어떤 기준이 필요한지를 먼저 봅니다. 배송 제약 VOC는 안내 구조 개선으로, 환불·교환 문의는 의도 선택값 구조로 연결해왔고, 채널톡 상담 매크로와 ARS 자동응대 멘트를 상황별로 분리해 문의량 증가·연휴·업무외 시간에도 동일한 기준으로 응대할 수 있도록 운영해왔습니다.

초록마을에서는 B2C 고객 VOC를 응답 시나리오와 자동응대 운영 개선 과제로 연결했고, 카카오VX에서는 제휴사별로 상이하던 예약·취소·위약 정보를 공통 확인 항목 중심으로 구조화해 어드민 정보 확인 기준으로 정리했습니다. 처음 접하는 도메인도 빠르게 구조화해 고객과 운영 담당자가 이해할 수 있는 응대 언어로 바꾸는 것이 제 강점입니다.

Case 01

고객 접점 자동응대 문구 운영 — 채널톡 상담 매크로 + ARS 안내 멘트 6종

Problem

문의량 증가, 업무외 시간, 연휴, 상담원 보호처럼 상황에 따라 고객에게 안내해야 할 정보가 달라졌습니다. 동일한 안내만으로는 처리 가능 시점이나 대체 채널을 충분히 설명하기 어려워, 상황별 자동응대 문구와 상담 매크로를 분리해 운영할 필요가 있었습니다.

연휴·점심시간처럼 처리 시점이 달라지는 상황과, 상담원 보호가 필요한 상황까지 같은 멘트로 안내하면 고객은 정확한 처리 시점을 알기 어렵고, 상담원은 불필요한 응대 부담에 노출될 수 있었습니다.

A 채널톡 상담 매크로 설계·운영

반복 문의에 대한 상담 매크로와 표준 답변을 직접 작성해, 동일한 유형의 문의는 같은 기준과 표현으로 안내되도록 정리했습니다. 그 결과 응대 처리 속도와 답변 일관성을 함께 높였습니다.

B ARS 안내 멘트 6종 작성·운영

Matrix Cloud IPCC에서 ARS 안내 멘트 6종을 직접 작성·운영했습니다. 문의량 증가, 점심시간, 업무외시간, 설/추석 연휴, 기본 인사말 등 상황별로 필요한 정보(처리 가능 시점, 대체 채널 안내, 문의 유형별 안내 범위)를 구분해 시나리오를 분리했습니다.

C 상담원 보호 기준 반영

기본 인사말에는 폭언·성희롱 발생 시 상담 중단이 가능하다는 법적·정책적 문구를 반영해, 고객 안내와 상담원 보호 기준을 함께 설계했습니다.

Result

상황별로 분리된 자동응대 멘트와 매크로를 통해 동일한 기준으로 고객 안내가 이뤄졌고, 상담원 보호·연휴처럼 운영 리스크가 있는 상황에도 일관된 대응이 가능해졌습니다.

ARS 멘트 6종 운영
채널톡 상담 매크로 표준화 · 상황별 시나리오 분리 · 상담원 보호 기준 반영

실제 화면

Insight

· 자동응대 문구는 단순 안내가 아니라, 고객 안내 리스크와 운영 리스크를 함께 설계하는 일입니다.

· 상황별 시나리오를 분리하면, 같은 채널에서도 고객이 더 정확한 정보를 받을 수 있습니다.

· 챗봇 운영에서도 같은 방식으로, 상황별 분기와 안전한 표현 기준을 설계할 수 있다고 생각합니다.

Case 02

고객 의도 기반 환불·교환 입력 구조 재설계 — 재확인 왕복 해소

Problem

환불·교환 등 고객이 원하는 해결방법이 별도 선택값으로 분리되어 있지 않아, 자유 텍스트 안에서 고객 의도를 다시 확인해야 하는 구조였습니다.

고객 의사 확인 없이 임의 처리할 경우 분쟁 리스크가 있어, 문의 접수 단계에서 고객이 원하는 해결방법을 먼저 선택하도록 하는 구조가 필요했습니다.

A 1:1 문의 접수 단계 '원하는 해결방법' 선택 필드 신설

1:1 문의 화면에 '원하는 해결방법' 선택 필드를 신설해 고객이 문의 작성 시 환불/교환 의사를 먼저 선택하도록 하고, 해당 값이 CRM의 해결방법 필드로 노출되도록 개선안을 정리했습니다.

B 기존 CRM 영역 활용 · 개발 범위 최소화

답변 작성일과 중복되는 '확인일시' 영역을 '해결방법' 필드로 대체하는 방향을 제안해, 별도 개발 범위를 늘리지 않고 구조 변경이 가능한 지점을 확인했습니다.

Result

고객 의도 확인을 위한 추가 답변 왕복을 줄이고, 담당자가 문의 접수 단계에서 해결방법 선택값을 바로 확인할 수 있어 후속 처리 기준이 더 명확해졌습니다.

재확인 왕복 해소 · 처리 기준 명확화
자유 텍스트 → 해결방법 선택값 · CRM 필드 연결 · 개발 범위 최소화

실제 화면

Insight

· 응대 단계에서 발생하는 재확인 비용은 대부분 입력 단계의 구조 문제에서 시작됩니다.

· 자유 텍스트는 유연해 보이지만, 실제로는 의도를 흐리는 구조입니다.

· 큰 개발 변경 없이 기존 필드 활용 방식만 다시 설계해도 운영 비용을 빠르게 줄일 수 있습니다.

Case 03

반복 VOC 기반 배송 제약 안내 구조 개선 — 개발 구현 제약 속 고객 혼선 최소화

Problem

배송 가능 요일이 다른 상품이 장바구니에 함께 담기면 주문이 차단됐지만, 고객에게는 기존 품절형 메시지만 노출되어 실제 원인을 알기 어려웠습니다. 고객은 이를 품절이나 시스템 오류로 인식했고, 동일한 문의가 일 6~10건 반복됐습니다.

핵심 문제는 고객의 이해 부족이 아니라, 주문이 막히는 시점에 시스템이 실제 차단 사유를 설명하지 못하는 UX 구조에 있었습니다.

A Fail-soft UX 설계

실제 원인은 상품별 배송 가능 요일이 다른 데 있었지만, 배송 가능 요일·상품 조합·도착 가능일을 모두 반영해 차단 로직을 전면 개편하기에는 개발 구현 난도가 높고 영향 범위가 큰 상황이었습니다.

그래서 차단 로직 자체를 바꾸기보다, 장바구니 단계에서 상품별 배송 가능 요일을 subtext로 함께 안내하는 방식을 제안했습니다. 고객이 차단 메시지를 보더라도 상품 옆 안내로 원인을 확인하고, 필요한 경우 상품을 분리하거나 제외해 주문을 조정할 수 있도록 한 것입니다.

또한 특정 상품에 한정되지 않고 다른 주의상품에도 재사용할 수 있도록, 라벨을 상품별로 다르게 적용 가능한 구조를 함께 제안했습니다. 데이터 자료와 함께 개발팀에 공유했고, 제안은 즉시 수용되어 당일 구현됐습니다. 이후 유사한 배송 제약이 있는 상품에도 같은 구조로 확장 적용됐습니다.

Result

반복 문의는 일 6~10건 수준에서 0건 수준으로 감소했습니다. 고객이 품절이나 시스템 오류로 오인하던 문제를, 상품별 배송 가능 요일 안내를 통해 원인을 확인할 수 있는 구조로 바꾼 결과입니다.

일 6~10건 → 0건 수준
반복 문의 해소 · 개발팀 제안·당일 구현 · 유사 케이스로 확장 적용

실제 화면

Insight

· 같은 정보를 충분히 안내하지 않을 때, 고객은 시스템 오류로 인식합니다.

· 차단 로직 전체를 바꾸기 어려운 상황에서도, 막히는 시점에 이유를 보여주는 fail-soft UX로 고객 혼선을 줄일 수 있습니다.

· 고객 접점에서 발견한 반복 패턴은 개발 구현 범위와 운영 현실을 함께 고려할 때 실제 개선으로 연결될 수 있습니다.

Case 04

AI·자동화 기반 반복 처리 효율화 — 반복 처리 7→1단계 축소와 내부 조회 구조 개선

Problem

대량 AS/재배송·반품 처리 시 동일 항목을 반복 입력해야 했고, 처리 건수가 늘어날수록 입력 피로도와 기준값 오류 가능성이 커졌습니다. 특히 귀책 대상, 처리 사유, 보상 기준처럼 후속 정산·집계에 연결되는 값은 한 번 잘못 입력되면 운영 데이터 전체가 왜곡될 수 있었습니다.

또한 상품 문의나 품질 이슈 처리 시 담당 MD와 상품코드를 확인하려면 매번 엑셀이나 별도 자료를 열어야 했고, 반복 조회와 이관 과정에서 처리 시간이 누적됐습니다.

A 반복 처리 자동화 — 7단계 → 1단계

Claude의 도움을 받아 Chrome Extension을 구현하고, AS/재배송·반품 등록 시 반복 입력되는 주요 항목이 단축키 한 번으로 자동 입력되도록 설계했습니다. 기존에는 주문 확인, 값 입력, 사유 선택, 상태 변경 등 여러 단계를 반복해야 했지만, 반복 입력 구간을 자동화해 처리 동선을 7단계에서 1단계로 줄였습니다.

해당 방식으로 AS/재배송 1,151건 이상을 처리했으며, 이후 반복 업무에도 계속 활용하고 있습니다.

다만 모든 단계를 자동화하지는 않았습니다. 귀책 판단, 예외 케이스 확인, 최종 등록처럼 비용·정산·고객 안내에 영향을 주는 구간은 담당자가 직접 확인하도록 남겨 오류 리스크를 낮췄습니다.

B Slack 기반 내부 조회 구조 구축

상품 문의나 품질 이슈 처리 시 담당 MD와 상품코드를 확인하는 과정도 반복적으로 발생했습니다. 기존에는 엑셀이나 별도 자료를 열어 검색해야 했기 때문에, 문의 이관 전 확인 시간이 계속 누적됐습니다.

Slack API와 Apps Script를 활용해 /담당자 슬래시 커맨드 조회 인터페이스를 구축했습니다. 상품명 일부 또는 상품코드를 입력하면 담당 MD와 상품코드가 즉시 조회되고, 결과는 입력자에게만 노출되도록 구성했습니다.

이를 통해 상품 문의 이관 전 내부 조회 동선을 줄이고, 담당자 확인 기준을 팀원들이 동일하게 사용할 수 있도록 정리했습니다.

C AI를 실무 파트너로 활용

Claude와 ChatGPT는 운영 기준 정리, 자동화 로직 설계 보조, 디버깅, 리스크 표현 검토, VOC 분류와 문서 초안 작성에 활용했습니다.

AI가 만든 결과를 그대로 사용하는 방식이 아니라, 실제 정책·원문·운영 데이터와 대조해 검수하는 방식으로 사용했습니다. 이 활용성을 인정받아 AI 도구를 공식 업무 도구로 승인받아 실무에 적용했습니다.

Result

반복 입력 업무는 7단계에서 1단계로 줄였고, AS/재배송 1,151건 이상을 처리하는 데 활용했습니다. 내부 조회 업무는 Slack 명령어 기반으로 전환해 담당 MD·상품코드 확인 동선을 단축했습니다.

자동화 대상과 사람의 판단이 필요한 구간을 분리해, 처리 속도뿐 아니라 기준값 일관성과 오류 감소까지 함께 개선했습니다.

7→1단계 · AS/재배송 1,151건 처리
반복 입력 동선 단축 · 기준값 일관성 개선 · 내부 조회 구조 전환 · AI 공식 업무 도구 승인

실제 화면

Insight

· 자동화의 목적은 속도가 아니라, 기준값 일관성과 오류 감소입니다.

· 모든 단계를 자동화하지 않고 리스크 구간은 사람에게 남기는 것이 운영 안정성을 만듭니다.

· AI는 답을 대신하는 도구가 아니라, 운영 기준을 더 빠르고 정확하게 정리하기 위한 실무 파트너입니다.

Case 05

카카오VX 제휴사 정책 정보 구조 표준화 — 카카오골프파트너스 어드민 정보란 정리

Problem

골프장 400여 곳의 예약·취소·위약 정보가 제휴사별로 카카오골프파트너스 어드민에 입력되어 있었지만, 정보 위치와 표현 방식이 제휴사마다 달랐습니다.

일부 골프장은 위약 적용 범위나 동반자 제한 여부 같은 항목이 비어 있거나 표현이 불명확해, 운영 담당자가 문의를 처리할 때마다 전체 정보를 다시 확인해야 했습니다.

A 반복 확인 정보의 공통 속성 도출

400여 개 제휴 골프장의 카카오골프파트너스 어드민 정보란을 확인하고, 예약실 연락처, 운영시간, 취소 가능 기한, 위약 적용 범위, 위약금 입금 계좌, 동반자 제한 여부 등 운영 담당자가 반복적으로 확인하는 정보의 공통 속성을 도출했습니다.

B 정보 순서·표현 구조 표준화

골프장별로 흩어져 있던 정보 위치와 표현을 일정한 순서와 문장 구조로 맞춰, 운영 담당자가 필요한 정보를 빠르게 찾고 오안내 가능성을 줄일 수 있도록 정리했습니다.

C 누락 정보 확인 및 보완 입력

정보가 누락되었거나 표현이 불명확한 경우에는 골프장에 직접 확인해 카카오골프파트너스 어드민 정보란에 보완 입력했습니다.

Result

제휴사별로 흩어져 있던 정책 정보가 공통 순서와 표현 기준으로 정리되고 누락된 정보가 보완되면서, 운영 담당자가 더 빠르고 정확하게 정보를 확인할 수 있는 기반이 마련되었습니다.

400+ 제휴사 정책 정보 구조 표준화
정보 순서·표현 기준 통일 · 누락 정보 확인·보완 입력 · 오안내 가능성 감소

Insight

· 정보가 있다고 기준이 되는 것은 아닙니다. 누락과 모호함까지 확인해야 실제로 쓸 수 있는 기준이 됩니다.

· 흩어진 정보는 실제 처리 순서에 맞게 재배열되어야 운영 기준이 됩니다.

· 파트너 운영에서 중요한 것은 모든 제휴사를 같게 만드는 게 아니라, 다른 정책도 동일한 구조로 확인할 수 있게 만드는 것입니다.

Sub Case

미출 문자 자동화 — 고객 안내 문구·발송 데이터 자동 생성

Problem

미출(품절·재고부족)이 발생하면 고객에게 안내 문구를 보내야 했는데, 문구 작성부터 발송 대상 데이터 정리까지 매번 수동으로 작성·복사·입력해야 했습니다. 발송 건수가 늘어날수록 반복 작업 시간이 누적되고, 입력 과정에서 오류가 생길 가능성도 있었습니다.

A 안내 문구·발송 데이터 자동 생성

Google Sheets에서 고객 안내 문구와 발송 대상 데이터를 자동으로 생성하도록 구성하고, 결과를 mplace 발송 화면으로 이동해 발송 준비를 빠르게 할 수 있도록 정리했습니다. 기존에 수동으로 문구를 작성·복사·입력하던 단계를 줄이는 데 목적을 두었습니다.

또한 취소예정 건은 조건부 서식으로 자동 강조되도록 설정해, 처리 우선순위가 높은 케이스를 누락 없이 구분할 수 있도록 했습니다.

사용 방법은 노션 가이드 문서로 정리해, 발송 건부터 순차적으로 적용하며 사용 중 불편한 점이나 오류를 댓글로 공유받아 보완했습니다.

Result

문구 작성과 발송 데이터 준비 단계가 줄어 반복 작업 부담이 줄었고, 동일한 형식으로 안내 문구가 생성되어 표현 일관성도 함께 확보됐습니다.

문구 작성·발송 데이터 준비 단계 축소
Google Sheets 자동 생성 · mplace 발송 화면 이동 · 가이드 문서화

실제 화면

Insight

· 반복되는 수동 작업은 작더라도 누적되면 큰 시간 비용이 됩니다.

· 자동화를 적용한 뒤에도 사용 중 피드백을 받아 계속 보완하는 과정이 필요합니다.
