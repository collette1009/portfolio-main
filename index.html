CX는 고객 접점에서 발견한 문제를 제품·운영 구조로 바꾸는 일이라고 생각합니다. 저는 고객의 반복 문의에서 패턴을 읽고, 그것을 제품·운영 개선 과제로 바꾸는 방식으로 일해왔습니다.

프로모션 오인 VOC 173건을 전수 분류해 82%가 동일 구조 원인임을 데이터로 확인했고, 이를 바탕으로 운영 기준을 수립했습니다. 배송 VOC 패턴에서는 UX 구조 문제를 재정의해 개발팀에 직접 제안했고, 당일 구현까지 이끌었습니다. 그 결과 관련 반복 인입은 0건 수준으로 줄었습니다.

초록마을에서는 B2C 고객 VOC를 제품·운영 개선 과제로 연결했고, 카카오VX에서는 제휴사별로 상이하게 관리되던 예약·취소·위약 기준을 표준화해 상담 및 운영 판단 기준으로 정리했습니다.

처음 접하는 도메인 앞에서도 멈추지 않습니다. 택배 표준약관과 물류 계약서도 처음이었지만, Claude로 쟁점을 정리하고 NotebookLM으로 원문을 교차 확인해 정산·배상 판단 근거를 만들었습니다. 운영 판단 기준이 없던 환경에서는 처리 기준과 에스컬레이션 구조를 직접 설계해 경영진 보고 후 공통 운영 기준으로 정리했습니다.

어려운 지식을 빠르게 파악해 고객이 이해할 수 있는 언어로 바꾸는 것. 그것이 제가 새로운 도메인에 들어가는 방식입니다.

AI 도구도 단순 보조 수단이 아니라 실무 파트너로 활용해왔습니다. 비개발 직군에서도 AI 업무비를 공식 승인받았고, Chrome Extension을 직접 구현해 반복 업무 동선을 7단계에서 1단계로 줄였습니다. AI를 실제 CX 운영 개선에 적용해본 사람으로 기여하고 싶습니다.

Case 01

배송 제약 VOC를 Fail-soft UX로 전환 — 개발팀 제안·당일 구현·반복 문의 0건 수준

Problem

매장배송 특성상 매장마다 재고 상황에 따라 상품별 배송 가능일이 다르게 적용되는데, 배송 가능일이 다른 상품이 장바구니에 함께 담기면 주문이 차단됐지만 고객에게는 그 이유가 충분히 안내되지 않았습니다. 그런 상품 조합이 등록될 때마다 고객은 이를 품절이나 시스템 오류로 인식했고, 동일한 유형의 문의가 반복됐습니다.

핵심 문제는 고객의 이해 부족이 아니라, 주문이 막히는 시점에 시스템이 이유를 설명하지 못하는 UX 구조에 있었습니다.

A Fail-soft UX 설계

모든 예외 조건을 시스템에서 완벽히 분기하기는 어려웠기 때문에, API 응답값으로 판단 가능한 조건만 남겨 최소 실행 단위의 개선안을 설계했습니다.

고객이 주문 불가 이유를 이해하고 흐름을 이어갈 수 있도록 장바구니 내 subtext 안내 구조를 직접 기획했고, 데이터 자료와 함께 개발팀에 제안했습니다. 제안은 즉시 수용되어 당일 구현됐습니다.

B 운영 기준 확산

해당 subtext 구조는 이후 유사한 안내 케이스에도 적용 가능한 기준으로 확장됐습니다. 단순 문구 추가가 아니라, 고객이 막히는 시점에 필요한 정보를 제공하는 유사 안내 케이스로 확장 적용됐습니다.

Insight

· 같은 정보를 충분히 안내하지 않을 때, 고객은 시스템 오류로 인식합니다.

· 모든 예외를 분기하기보다, 막히는 시점에 이유를 보여주는 UX가 더 실용적입니다.

· 고객 접점에서 발견한 패턴도 운영 기준이 있으면 제품 표준으로 확장됩니다.

Case 02

고객 의도 기반 환불·교환 입력 구조 재설계 — AS 재확인 왕복 95%+ 감소

Problem

환불·교환 사유가 자유 텍스트로 입력되던 구조였습니다. 고객의 진짜 의도가 자유 텍스트 안에 묻혀 응대 단계에서 다시 확인해야 하는 왕복이 누적되고 있었습니다.

고객이 본인 의도를 정확히 풀어 쓰지 않으면 처리 담당자는 안전한 선택을 위해 추가 확인을 해야 했고, 그만큼 리드타임이 길어졌습니다.

A 자유 텍스트 → 필수 선택값 구조화

고객 의도를 빈도순으로 분석해, 의도 기반 필수 선택값으로 입력 필드를 재구성했습니다. 입력 단계에서 의도가 정해지니 응대 단계의 재확인이 필요한 시점이 사라졌습니다.

B 중복 DB 필드 활용 · 개발 범위 최소화

새 컬럼을 만들지 않고 중복 활용 가능한 DB 필드를 활용하는 스펙을 직접 설계해 개발 범위를 최소화했고, 빠르게 반영 가능한 형태로 유관부서와 협의했습니다.

C 결과

입력 단계에서 의도가 구조화되니 응대 단계의 재확인 왕복이 95% 이상 감소했고, 환불·교환 처리 리드타임이 단축됐습니다.

· 큰 개발 변경 없이 기존 필드 활용 방식만 다시 설계해도 운영 비용을 빠르게 줄일 수 있습니다.

Case 03

카카오VX 400+ 제휴사 정책 표준화 — 운영 기준을 동일하게 참조할 수 있도록

Problem

골프장 400여 곳의 취소 정책·위약금 기준·동반자 변경 규정이 제각각이었습니다. 어드민에는 데이터가 있었지만, 제휴사별 정책 전달 형식과 표현이 달라 담당자가 바로 판단할 수 있는 기준으로 정리되어 있지 않았습니다.

동일 유형 문의에도 팀원마다 안내가 달라지는 상황이 발생했고, 오안내와 재문의가 반복되며 처리 품질 편차도 함께 커졌습니다.

A 400여 곳 정책 전수 정리 · 단일 판단 체계 수립

400여 개 제휴 골프장의 정책을 중요도순으로 재구조화하고, 예약·취소·위약·동반자 변경 기준을 유형별로 분류했습니다. 반복 문의가 발생하는 구간을 VOC 기준으로 다시 정리하고, 담당자가 동일 기준으로 판단할 수 있도록 운영 가이드와 Knowledge Base를 재정비했습니다.

B 정책 최신화 흐름 · 신규 인력 온보딩

정책 변경이 발생할 때는 어드민 기준이 최신 상태로 반영되도록 내부 공유 흐름을 정리했고, 신규 인력이 빠르게 기준을 익힐 수 있도록 온보딩 자료에도 반영했습니다.

C 결과

동일 유형 문의에 대한 운영 기준이 통일되었고, 정책 해석 차이로 인한 오안내와 재문의 가능성을 줄였습니다. 제휴사별 정책이 개인 숙련도에 의존하지 않고 팀 전체가 동일 기준으로 참조할 수 있게 되었으며, 신규 인력 온보딩 시간과 처리 품질 편차를 줄이는 데 기여했습니다.

Insight

· 흩어진 정보는 자동으로 기준이 되지 않습니다 — 누군가 의도적으로 구조화해야 합니다.

· 처리 품질은 사람의 숙련도가 아니라, 참조 가능한 기준이 있을 때 안정적으로 유지됩니다.

· 파트너 운영에서 큰 비용 중 하나는 응대 시간보다 기준 부재로 인한 해석 편차입니다.

Case 04

외부 파트너 계약 기반 정산 구조 재정의 — 배상 회수율 14.7배 개선

Problem

외부 파트너 귀책으로 발생한 배송 사고·물류 손실이 있었지만, 배상은 파트너사 관행에 따라 제한적으로 처리되고 있었습니다. 사고는 반복되는데 책임 기준과 비용 반영 구조가 명확하지 않아, 월 배상 회수액은 50만 원 수준에 머물러 있었습니다.

약관·계약 영역은 제가 처음 접하는 도메인이었지만 멈추지 않았습니다.

A 택배 표준약관 검토 · 근거 기반 협상 구조로 전환

택배 표준약관을 기준으로 파손·분실·배송 사고 시 청구 가능한 조건을 정리했습니다. Claude로 쟁점을 먼저 구조화하고, NotebookLM으로 원문 근거를 교차 확인해 사진·접수 기록 등 최소 증빙이 있을 경우 파트너에게 청구 가능한 기준을 세웠습니다. 기존 관행 중심의 처리 방식을 근거 기반 협상 구조로 전환했습니다.

B 물류 계약서 선공제 조항 확인 · CEO 보고·공통 운영 기준 정리

물류 계약서를 다시 검토하는 과정에서 기존 운영에서 활용되지 않던 선공제 조항을 확인했습니다. 해당 조항을 근거로 피해 유형, 비용 항목, 정산 기준을 재정리했고, CEO 보고를 거쳐 공통 운영 기준으로 정리했습니다.

Case 05

AI·자동화 기반 운영 효율화 — 반복 입력·집계·문서화 비용 축소

Problem

· 대량 처리 시 동일 항목을 반복 입력해야 했고, 처리 건수가 늘어날수록 입력 피로도와 기준값 오류 가능성이 커졌습니다.

· 귀책대상·처리 사유처럼 후속 정산·집계에 연결되는 값은 한 번 잘못 입력되면 운영 데이터 전체가 왜곡될 수 있었습니다.

· VOC 분류·집계·운영 기준 문서화 등 반복 업무에 시간이 많이 들고, 기준이 사람마다 조금씩 달라지는 문제도 있었습니다.

A 반복 입력·집계 자동화

Chrome Extension을 직접 구현해 재배송·반품 등록 시 주요 항목이 단축키 한 번으로 자동 입력되도록 설계했습니다. 처리 동선을 7단계에서 1단계로 줄였습니다.

Apps Script로 일일 자금집행 리포트의 자동 분류·발송 구조를 구축했고, Excel VBA로 중복 감지·자동 합산·대표행 집계 처리를 정리했습니다.

B 리스크 구간은 사람에게 남김

귀책 판단, 예외 케이스 확인, 최종 등록처럼 비용·정산·고객 안내에 영향을 주는 구간은 담당자가 직접 확인하도록 남겼습니다.

자동화의 목적을 단순 속도가 아니라 반복 오류를 줄이고 기준값을 표준화하는 데 두었습니다.

C AI를 실무 파트너로 활용

Claude는 운영 기준 정리, 자동화 로직 설계 보조, 디버깅, 리스크 표현 검토에 사용했습니다. NotebookLM과 GPT는 VOC 분류, 약관·계약 원문 교차 확인, 운영 기준 초안 작성에 활용했습니다.

단순히 AI 답변을 쓰는 것이 아니라, 운영 기준을 더 빠르고 정확하게 만드는 실무 파트너로 활용했습니다. 이 활용성을 인정받아 비개발 직군에서도 AI 업무비를 공식 승인받았습니다.

Insight

· 자동화의 목적은 속도가 아니라, 기준값 일관성과 오류 감소입니다.

· 모든 단계를 자동화하지 않고 리스크 구간은 사람에게 남기는 것이 운영의 안정성을 만듭니다.

· AI는 답을 주는 도구가 아니라, 운영 기준을 정확하게 정리하는 데 쓰는 실무 파트너입니다.
