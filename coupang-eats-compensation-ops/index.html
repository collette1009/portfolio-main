CASE 01 / COMPENSATION POLICY

‘회수 없이는 보상 불가’였던 기준을, 택배사 자체 약관을 근거로 다시 협의했습니다.

Problem

파손·누수 사고에도 실물 회수를 먼저 요구하는 기준 때문에 고객이 깨진 유리나 식품을 보관해야 했고, 사고 처리와 배상 접수도 회수·입고 확인에 묶여 있었습니다.

Action

단순 예외 요청이 아니라 택배사 표준약관의 사전 통보 의무와 사고 발생 시 조치 의무를 기준으로, 실제 사고 상황에서 그 의무를 어떻게 이행할지 재질문했습니다. 이후 파트너와 사진을 통한 사고 확인·자체 폐기 방식의 처리 흐름을 협의했습니다.

Result

실물 회수 없이 사진으로 사고를 확인하는 프로세스가 제안·적용됐고, 비교 월 기준 택배사 배상 회수액은 50만원대에서 약 744만원으로 확대됐습니다.

Learning

파트너 협의는 ‘고객이 불편하다’는 주장보다 상대가 이미 가진 기준을 실제 운영 상황에 대입해 모순과 실행 책임을 묻는 방식이 더 효과적이었습니다.

핵심 · 약관을 보상 의무의 직접 근거로 과장하지 않고, 파트너의 통보·사고조치 기준을 협의 근거로 삼아 증빙·회수 프로세스를 재정렬
BEFORE

파손 확인 → 실물 회수 → 입고 확인 → 사고 접수/배상

→
AFTER

파손 확인 → 사진 증빙 → 사고 접수 → 고객 자체 폐기 가능

Problem

Result

CASE 04 / SYSTEM VALIDATION

배송조회 오류를 재현 가능한 조건으로 정리해 당일 수정까지 확인했습니다.

Problem

관리자 화면에서 배송조회 링크가 정상 동작하지 않아 운영자가 추가 확인을 반복해야 했습니다.

Action

오류 화면과 실패 조건을 재현해 개발팀에 전달하고 후속 확인을 이어갔습니다. 개발팀이 요청값 형식 문제를 확인해 프론트 수정을 진행했습니다.

Result

원인 확인과 수정이 같은 날 완료됐고 실제 동작까지 확인했습니다.

Learning

자동화·시스템은 정상 작동을 전제로 두기보다 운영자가 검증 가능한 실패 조건을 갖고 있어야 했습니다.

핵심 · 운영 오류 재현·증빙 → 개발 원인 확인 → 수정 완료까지 후속 검증
