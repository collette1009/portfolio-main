CASE 01

반복 VOC 기반 안내 구조 개선 — 장바구니 품절 오인 문의 감소

✕

Problem

배송 가능 요일이 다른 상품이 함께 담기면 주문이 차단됐지만, 고객에게는 기존 품절형 메시지만 노출되어 실제 원인을 알기 어려웠습니다. 동일한 문의가 일 6~10건 반복됐습니다. 핵심 문제는 주문이 막히는 시점에 실제 차단 사유를 보여주지 못하는 화면 구조였습니다.

What I Did

A
반복 VOC 원인 재정의

문제를 단순 품절 문의가 아니라, 차단 사유가 화면에 드러나지 않는 안내 구조 문제로 재정의했습니다.

B
개발 제약을 고려한 최소 개선안 제안

차단 로직 전체를 바꾸는 것은 영향 범위가 컸기 때문에, 장바구니 단계에서 상품별 배송 가능 요일을 subtext로 안내하는 방식을 제안했습니다. 유사한 배송 제약 상품에도 재사용할 수 있도록 라벨 구조로 정리했습니다.

C
개발팀 협의 및 유사 케이스 확장

반복 문의 데이터와 실제 고객 혼선 지점을 함께 공유해 개발팀에 개선안을 전달했고, 제안은 당일 반영되었습니다. 이후 유사한 배송 제약 상품에도 같은 안내 구조를 확장 적용했습니다.

일 6~10건 → 0건 수준
반복 문의 해소 · 개발팀 제안·당일 구현 · 유사 케이스로 확장 적용
실제 화면
UMOS ONE 연결

UMOS ONE의 모빌리티 서비스 'TAP!'에서도 배차, 결제, 차량 상태처럼 고객이 이해하기 어려운 시스템 제약이 발생할 수 있습니다. 시스템 전체를 바로 바꾸기 어렵더라도, 막히는 시점에 원인과 다음 행동을 화면에서 먼저 보여주면 반복 문의와 운영 인입을 줄일 수 있습니다.

Insight

같은 정보를 충분히 안내하지 않으면 고객은 시스템 오류로 받아들입니다. 차단 로직 전체를 바꾸기 어려운 상황에서도, 막히는 시점에 이유를 먼저 보여주면 혼선을 줄일 수 있습니다.

CASE 02

CS 처리 기준·답변 검수·코칭 체계 정비

✕

Problem

조직 변동으로 CS 전담 인력이 축소된 상황에서 디자인·콘텐츠·상품 등 다양한 부서의 담당자가 문의 처리에 투입됐습니다. CS 전담자가 아닌 담당자들이 문의를 처리하면서 안내 범위, 확정 표현, 책임 주체 표현이 달라질 수 있었습니다.

What I Did

A
이슈 유형별 확인 순서·권장 문구 정리

이슈 유형별로 확인 순서, 권장 문구, 금지 표현, 타부서 판단이 필요한 구간을 정리해 누가 처리하든 같은 기준으로 판단할 수 있도록 했습니다.

B
답변 품질·처리 방향 검수·코칭

문의 처리에 투입된 타부서 담당자의 답변 품질과 처리 방향을 검수하며, 상황 요약 → 위험 포인트 → 권장 문구 → 다음 조치 순서로 피드백 구조를 만들었습니다.

C
에스컬레이션 기준 정리·온보딩 가이드화

후속 확인과 에스컬레이션 기준을 정리하고, 담당자가 바뀌어도 같은 기준으로 운영이 이어질 수 있도록 온보딩 가이드로 문서화했습니다.

응대 품질 편차·에스컬레이션 누락 리스크 감소
여러 부서 담당자가 투입된 상황에서도 같은 기준으로 처리 가능
UMOS ONE 연결

서비스가 확장되는 과정에서는 CS 전담 인력뿐 아니라 유관부서와 함께 이슈를 처리해야 하는 상황이 생길 수 있습니다. 상담 기준과 검수·코칭 체계가 마련되어 있으면 담당자가 늘어나거나 바뀌어도 같은 기준으로 응대 품질을 유지할 수 있습니다.

Insight

조직 구조가 바뀌어도 처리 기준과 검수 기준이 남아 있으면, 담당자가 달라져도 응대 품질을 일정하게 유지할 수 있습니다.

CASE 03

대량 이슈 처리 자동화와 환불계좌 사전 검증 프로세스

✕

Problem

대량 미출고·배송 지연 이슈 대응 과정에서 동일 항목 반복 입력과 후속 확인 누락 리스크가 컸습니다. 환불계좌 오류가 발생하면 고객 재확인·지출요청서 수정·재이체 요청이 반복됐습니다.

What I Did

A
Chrome Extension 기반 반복 입력 자동화

생성형 AI의 도움을 받아 Chrome Extension을 구현해 AS·재배송·반품 등록 처리 동선을 7단계에서 1단계 수준으로 줄였습니다.

B
Google Sheets 기반 미출고 안내 문자 자동화

고객별 안내 문구와 발송 데이터를 Google Sheets에서 자동 생성해 SMS 발송 플랫폼으로 바로 이동할 수 있도록 구성했습니다. 수동으로 문구를 작성·복사·입력하던 단계를 줄였습니다.

C
외부 예금주 조회 API 기반 환불계좌 사전 검증

온라인 환불계좌 오류로 재확인·재이체 요청이 반복되는 문제를 확인하고, 외부 예금주 조회 API를 활용해 지출요청 전 계좌 유효성과 예금주 일치 여부를 일괄 검증하는 파일을 구성했습니다.

반복 처리 동선 7→1단계 · 대량 이슈 1,151건+ 대응
수기 확인·재확인 부담 축소 · 환불계좌 검증 단계 구성
실제 화면
UMOS ONE 연결

UMOS ONE의 플릿 운영에서도 차량·정산·사고 관련 반복 조회와 입력이 늘어날 수 있습니다. 반복 구간은 자동화하고, 계좌·비용처럼 확인이 꼭 필요한 구간은 사전 검증 단계로 남기면 운영 인력을 늘리지 않고도 안정적으로 확장할 수 있습니다.

Insight

자동화의 목적은 속도가 아니라 기준값 일관성과 오류 감소입니다. 확인이 필요한 구간은 그대로 남기고, 반복 구간만 자동화하는 판단이 중요합니다.

CASE 04

외부 파트너 사고·보상·정산 기준 재정렬

✕

Problem

사고 접수, 증빙, 보상, 정산 기준이 분리되지 않으면 책임 주체가 흐려지고 재민원·비용 누락으로 이어질 수 있었습니다. 물류 파트너 전환 이후 파트너 귀책 가능성이 있는 사고가 반복됐지만, 이를 월별 피해현황과 정산 협의 자료에 어떻게 반영할지에 대한 실무 적용 기준은 정리되어 있지 않았습니다.

What I Did

A
원문 근거 기반 사고·증빙 기준 재정리

택배 표준약관과 실제 사고 접수 흐름을 기준으로, 사고 접수 기록과 현장에서 확보 가능한 외부 파손·오염 증빙을 기준으로 처리할 수 있도록 논점을 정리했습니다.
