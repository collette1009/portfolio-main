초록마을에서는 배송 지연, 미출고, 환불·교환, 품질 민감 이슈처럼 고객 안내와 내부 판단 기준이 함께 필요한 문의를 주로 다뤘습니다. 반복 문의가 생기면 고객이 실제로 헷갈리는 지점과 내부에서 다시 확인되는 기준을 함께 보고, 상담 담당자가 같은 기준으로 답변할 수 있도록 FAQ와 처리 기준을 정리했습니다.

또한 택배사·물류사·3PL 등 외부 운영 파트너와 연결된 사고·보상·정산 이슈는 접수, 이관, 비용 판단 기준을 나누어 정리했습니다. 택배사·물류사에서 전달한 확정액을 그대로 수용하기보다 내부 기준과 실제 발생 원인을 확인해 재정산 필요 여부를 검토했고, 시스템 장애 상황에서는 대체 흐름을 확인해 운영 공백을 줄였습니다.

CASE 01

고객센터 자동응대/상담 기준 운영 — 채널톡 상담 매크로 + ARS 안내 멘트 6종

✕

Problem

문의량 증가, 업무외 시간, 연휴, 상담 담당자 보호처럼 상황에 따라 고객에게 안내해야 할 내용이 달라졌습니다. 같은 안내문으로 연휴·점심시간처럼 처리 시점이 달라지는 상황과 상담 담당자 보호가 필요한 상황까지 함께 안내하면, 고객은 정확한 처리 시점을 알기 어렵고 상담 담당자는 불필요한 응대 부담에 노출될 수 있었습니다.

What I Did

A
채널톡 상담 매크로 설계·운영

반복 문의에 대한 상담 매크로와 표준 답변을 직접 작성해, 동일한 유형의 문의는 같은 기준과 표현으로 안내되도록 정리했습니다.

B
ARS 안내 멘트 6종 작성·운영

Matrix Cloud IPCC에서 ARS 안내 멘트 6종을 작성·운영했습니다. 문의량 증가, 점심시간, 업무외시간, 설/추석 연휴, 기본 인사말 등 상황별로 필요한 정보(처리 가능 시점, 대체 채널 안내, 문의 유형별 안내 범위)를 구분해 멘트를 나눴습니다.

C
상담 담당자 보호 기준 반영

기본 인사말에는 폭언·성희롱 발생 시 상담을 중단할 수 있다는 정책 문구를 반영해, 고객 안내와 상담 담당자 보호 기준을 함께 정리했습니다.

Result

상황별로 분리된 자동응대 멘트와 매크로를 통해 동일한 기준으로 고객 안내가 이뤄졌고, 상담 담당자 보호·연휴처럼 운영 리스크가 있는 상황에도 일관된 대응이 가능해졌습니다.

CASE 02

고객 의도 기반 환불·교환 입력 구조 개선 — 재확인 왕복 줄이기

✕

Problem

환불·교환처럼 고객이 원하는 해결방법이 별도 선택값으로 분리되어 있지 않아, 자유 텍스트 안에서 고객 의도를 다시 확인해야 하는 구조였고, 의사 확인 없이 임의로 처리할 경우 분쟁 리스크가 있었습니다.

What I Did

A
1:1 문의 접수 단계 '원하는 해결방법' 선택 필드 신설

1:1 문의 화면에 '원하는 해결방법' 선택 필드를 신설해 고객이 문의 작성 시 환불/교환 의사를 먼저 선택하도록 하고, 해당 값이 CRM의 해결방법 필드로 노출되도록 개선안을 정리했습니다.

B
기존 CRM 영역 활용 · 개발 범위 최소화

답변 작성일과 중복되는 '확인일시' 영역을 '해결방법' 필드로 대체하는 방향을 제안해, 별도 개발 범위를 늘리지 않고 구조를 바꿀 수 있는 지점을 확인했습니다.

Result

고객 의도 확인을 위한 추가 답변 왕복을 줄이고, 담당자가 문의 접수 단계에서 해결방법 선택값을 바로 확인할 수 있어 후속 처리 기준이 더 명확해졌습니다.

재확인 왕복 감소 · 처리 기준 명확화
자유 텍스트 → 해결방법 선택값 · CRM 필드 연결 · 개발 범위 최소화
실제 화면

Insight

응대 단계에서 발생하는 재확인 비용은 대부분 입력 단계의 구조 문제에서 시작됩니다. 큰 개발 변경 없이 기존 필드를 다르게 활용하는 방식만 다시 설계해도 운영 비용을 빠르게 줄일 수 있습니다.

CASE 03

반복 VOC 기반 배송 제약 안내 개선 — 개발 제약 속 고객 혼선 줄이기

✕

Problem

배송 가능 요일이 다른 상품이 함께 담기면 주문이 차단됐지만, 고객에게는 기존 품절형 메시지만 노출되어 원인을 알기 어려웠고, 동일한 문의가 일 6~10건 반복됐습니다. 핵심 문제는 주문이 막히는 시점에 실제 차단 사유를 보여주지 못하는 화면 구조였습니다.

What I Did

A
최소 개선안 설계 — subtext 안내

차단 로직 전면 개편은 구현 난도가 높고 영향 범위가 컸기 때문에, 장바구니 단계에서 상품별 배송 가능 요일을 subtext로 안내하는 현실적인 개선안을 제안했습니다. 특정 상품에 한정되지 않고 다른 주의상품에도 재사용할 수 있도록 라벨을 상품별로 다르게 적용 가능한 구조도 함께 제안했습니다. 관련 데이터와 함께 개발팀에 공유했고, 제안은 즉시 수용되어 당일 구현된 뒤 유사한 배송 제약 상품에도 같은 구조로 확장 적용됐습니다.

같은 정보를 충분히 안내하지 않으면 고객은 시스템 오류로 받아들입니다. 차단 로직 전체를 바꾸기 어려운 상황에서도, 막히는 시점에 이유를 먼저 보여주면 혼선을 줄일 수 있습니다. 상품·혜택·수령 일정이 촘촘한 서비스에서도 같은 방식으로 적용할 수 있다고 생각합니다.

CASE 04

외부 파트너 사고·배상 기준 재정렬 — 원문 근거로 증빙·정산 기준 구조화

✕

Problem

택배·물류 사고 발생 시 택배사, 물류사, 본사 간 증빙 요건과 비용 반영 기준이 달라 배상 처리가 지연되거나 회수로 이어지지 못하는 경우가 많았습니다. 파손 스캔이나 운송 중 훼손이 확인된 건도 회수, 송장 사진, 외부 박스 사진, 내품 사진 등 증빙 요건을 모두 충족하지 못하면 배상 처리로 이어지기 어려웠습니다. 물류 파트너 전환 이후에는 출고 누락·포장 불량·파손 등 파트너 귀책 가능성이 있는 사고가 반복됐지만, 이를 정산 비용에 반영할 기준이 정해져 있지 않았습니다.

What I Did

A
원문 근거 기반 사고·증빙·정산 기준 재정리

택배 표준약관과 실제 사고 접수 흐름을 기준으로, 택배사 시스템상 사고가 확인된 건은 회수·사진 3종을 일괄 요구하기보다 사고 접수 기록과 현장에서 확보 가능한 외부 파손·오염 증빙을 기준으로 처리할 수 있도록 논점을 정리했습니다. 이를 통해 증빙 병목 없이 배상 처리로 이어질 수 있는 흐름을 만들었습니다.

B
물류 계약서 기준으로 파트너 귀책 비용 차감 반영

물류 계약서 원문을 기준으로, 초록마을이 먼저 처리한 환불액·재배송비·CS 보상 비용을 익월 물류비 정산에서 차감 반영할 수 있는 기준을 정리했습니다. 파손·누락·지연 이슈를 비용 유형별로 나누어 정산 협의 자료로 정리하고, 파트너가 제시한 확정액을 그대로 수용하지 않고 재검토 후 재정산을 요청했습니다.

배상 회수액 월 50만 원 수준 → 약 745만 원 수준 (14.7배 수준 개선)
원문 근거 기반 증빙 기준 재정리 · 파트너 귀책 비용 정산 반영

Insight

외부 운영 파트너와 일할 때는 전달받은 금액을 그대로 받아들이지 않고, 내부 기준으로 한 번 더 확인하는 과정이 필요하다고 생각합니다. 위버스의 글로벌 배송이나 현장수령처럼 외부 조직과 맞물린 영역에서도 같은 방식으로 책임과 비용 기준을 정리할 수 있다고 봅니다.

CASE 05

AI·자동화 기반 반복 처리 효율화 — 반복 처리 7→1단계 축소

✕

Problem

대량 AS/재배송·반품 처리 시 동일 항목을 반복 입력해야 했고, 처리 건수가 늘어날수록 입력 피로도와 기준값 오류 가능성이 커졌습니다. 상품 문의·품질 이슈 처리 시 담당 MD와 상품코드를 확인하는 일도 매번 반복됐습니다.

What I Did

A
반복 처리 자동화 — 7단계 → 1단계

Claude의 도움을 받아 Chrome Extension을 구현해 처리 동선을 7단계에서 1단계로 줄였습니다 (AS/재배송 1,151건 이상 처리). 귀책 판단·예외 케이스처럼 비용에 영향을 주는 구간은 담당자가 직접 확인하도록 남겼습니다.

B
Slack 기반 내부 조회 구조 구축

Slack API와 Apps Script로 /담당자 슬래시 커맨드 조회 인터페이스를 구축해 담당 MD·상품코드를 즉시 조회할 수 있도록 했습니다.

C
AI를 실무 파트너로 활용

ChatGPT·Claude 활용성을 인정받아 AI 도구를 공식 업무 도구로 승인받아 실무에 적용했습니다.

7→1단계 · AS/재배송 1,151건 처리
반복 입력 동선 단축 · 기준값 일관성 개선 · AI 공식 업무 도구 승인
실제 화면

Insight

자동화의 목적은 속도가 아니라 기준값 일관성과 오류 감소이며, AI는 답을 대신하는 도구가 아니라 운영 기준을 정리하고 자동화 로직을 설계하는 데 쓰는 실무 도구라고 생각합니다.

CASE 06

카카오VX 제휴사 정책 정보 구조 표준화 — 카카오골프파트너스 어드민 정보란 정리

✕

Problem

골프장 400여 곳의 예약·취소·위약 정보가 제휴사별로 어드민에 입력되어 있었지만, 정보 위치와 표현 방식이 제휴사마다 달랐고, 일부 골프장은 위약 적용 범위나 동반자 제한 여부 같은 항목이 비어 있거나 표현이 불명확했습니다.

What I Did

A
반복 확인 정보의 공통 속성 도출

400여 개 제휴 골프장의 어드민 정보란을 확인하고, 예약실 연락처, 운영시간, 취소 가능 기한, 위약 적용 범위, 위약금 입금 계좌, 동반자 제한 여부 등 반복적으로 확인하는 정보의 공통 항목을 도출했습니다.

B
정보 순서·표현 구조 표준화

골프장별로 흩어져 있던 정보 위치와 표현을 일정한 순서와 문장 구조로 통일해, 운영 담당자가 필요한 정보를 빠르게 찾고 오안내 가능성을 줄일 수 있도록 정리했습니다.

C
누락 정보 확인 및 보완 입력

정보가 누락되었거나 표현이 불명확한 경우에는 골프장에 직접 확인해 보완 입력했습니다.

400+ 제휴사 정책 정보 구조 표준화
정보 순서·표현 기준 통일 · 누락 정보 확인·보완 입력 · 오안내 가능성 감소
Before
골프장별로 정보 위치·표현이 제각각이고, 일부 항목(위약 적용 범위·동반자 제한 여부 등)이 비어 있거나 표현이 불명확함
→
After
예약실 연락처 → 운영시간 → 취소 가능 기한 → 위약 적용 범위 → 위약금 입금 계좌 → 동반자 제한 여부 순서로 통일 정리

Insight

정보가 있다고 기준이 되는 것은 아닙니다. 누락과 모호함까지 확인해야 실제로 쓸 수 있는 기준이 됩니다. 제휴사 운영에서 중요한 것은 모든 제휴사를 같게 만드는 게 아니라, 다른 정책도 같은 순서로 확인할 수 있게 만드는 것입니다. 위버스의 멤버십·상품·이벤트·수령 조건처럼 정책이 많은 서비스에서도 같은 방식으로 기준을 정리할 수 있다고 생각합니다.
