CASE 01 · PRODUCT FLOW

배송 제약 VOC → 장바구니 안내 구조 개선

Problem

출고 가능 요일이 다른 상품을 함께 담으면 배송 가능한 날짜가 없어 주문이 막혔지만, 고객 화면에서는 원인이 충분히 드러나지 않아 같은 유형의 문의가 반복됐습니다.

Diagnosis

단순 안내 부족이 아니라 주문 불가 이유가 제품 화면에 드러나지 않는 문제로 보고 실제 조합을 재현했습니다.

Decision

전체 배송 로직을 바꾸기보다 충돌이 발생한 순간에 제한 이유를 보여주는 최소 기능으로 범위를 좁혔습니다.

Result · 제품 반영 후 관찰기간 내 동일 유형 문의 0건
CASE 02 · DATA STRUCTURE

환불·교환 고객 의도 입력 구조 재설계

Problem

고객이 원하는 해결방법이 자유 입력에 섞여 있어 담당자가 문의 내용을 다시 읽거나 추가 확인해야 했습니다.

Diagnosis

담당자의 숙련도 문제가 아니라, 접수 단계에서 필요한 정보가 구조화되지 않은 문제로 봤습니다.

Execution

1:1 문의에 ‘원하는 해결방법’ 선택값을 두고 해당 값이 CRM에서도 바로 확인되도록 연결했습니다.

Result · 재확인 왕복 95%+ 감소
CASE 03 · POLICY DECISION

1+1 VOC 173건 전수 분석 → 운영 정책 재설계

Analysis

173건을 전수 분류해 문구 미인지 142건(82.1%), 정책 기준 혼동 12건, 홀수 수량 알림 부재 19건으로 나눴습니다.

Decision

UI 전면 수정의 개발 복잡도와 문의 절대량을 비교해 즉시 개발하기보다 운영 정책으로 통제하는 편이 타당하다고 판단했습니다.

Execution

초회 예외와 재인입 종결 기준을 나눠 같은 상황에서 동일한 판단이 가능하도록 했습니다.

Result · 173건 중 82.1% 주원인 규명 · 제품 개선/운영 정책 중 해결 수단 선택
CASE 04 · AUTOMATION / OPERATING MODEL

물류 전환기 1,928건 우선순위 재설계 + 반복 입력 자동화

Problem

외부 물류 운영사 전환 직후 재배송 1,151건과 취소 777건이 동시에 발생했습니다.

Priority

취소는 접수 기한 이후 일괄 처리할 수 있지만 재배송은 지연될수록 고객에게 미치는 영향이 커져, 마감 시점과 영향도를 기준으로 재배송을 먼저 배치했습니다.

Automation

규칙이 명확한 정형 필드는 Chrome Extension으로 자동화하고, 귀책·금액·최종 제출처럼 책임이 필요한 판단은 담당자에게 남겼습니다.

Result · 총 1,928건 운영 · 반복 등록 7→1단계 · 필요 지원 인력 3→2명
CASE 05 · PARTNER / POLICY

택배 사고 증빙·회수 기준 재협의

Problem

파손 사고 고객은 사진 3종과 구매내역을 다시 제출하고 상품을 재포장해 회수될 때까지 보관해야 했습니다.

Diagnosis

모든 사고에 같은 증빙과 회수 절차를 적용하는 구조가 문제라고 보고 사고 확인에 꼭 필요한 수준을 다시 정리했습니다.

Negotiation

택배 표준약관에서 확인한 사고 처리 책임을 협상 근거 중 하나로 삼아 증빙 수준을 재논의했고, 실물 회수 없이 파손 사진으로 대체하는 접수안을 도출했습니다.

Result · 실물 회수 없이 파손 사진으로 대체하는 접수안 · 비교 월 배상 회수액 약 14.7배
