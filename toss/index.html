CASE 01

배송 제약 VOC 5건 → 당일 개선 → 추가 인입 0건

✕

PROBLEM

배송 가능일이 다른 상품을 함께 담았을 때 고객 화면에서는 왜 주문이 되지 않는지 알기 어려워, 운영 첫날 동일한 문의가 5건 누적됐습니다. 고객은 품절이나 시스템 오류로 오인하고 있었습니다.

DIAGNOSIS

배송 정책 자체보다 ‘어떤 상품 때문에 제약이 생겼는지 보이지 않는다’는 가시성 문제로 정의했습니다. 원인 상품 바로 아래에 배송 제약을 안내하는 구조를 개발·운영 담당자와 논의했습니다.

ACTION

장바구니에서 원인 상품과 배송 가능일 제약이 바로 보이도록 안내를 당일 반영했습니다. 이후 같은 유형의 문의가 추가로 들어오는지 계속 확인했습니다.

운영 첫날 5건 → 개선 후 추가 인입 0건VOC를 상담 문구 수정으로 끝내지 않고 고객 화면의 문제로 연결한 사례입니다.
실제 운영·개발 협업 과정의 일부입니다.
개선 후 장바구니에서 원인 상품과 배송 제약을 확인할 수 있도록 반영된 화면입니다.
CASE 02

프로모션 VOC 173건 전수 분석 → 82% 동일 오인

✕

PROBLEM

1+1/2+1 프로모션 문의가 반복됐지만, 단순히 ‘행사 문의가 많다’는 수준으로는 제품 개선이 필요한지 운영 기준이 필요한지 판단하기 어려웠습니다.

ANALYSIS

VOC 173건을 전수 분류해 143건, 약 82%가 행사 참여 방식 자체를 다르게 이해한 동일 유형의 오인임을 확인했습니다. 고객이 어떤 조건에서 증정품이 빠졌다고 인식하는지 유형을 나눴습니다.

DECISION

EC운영과 고객 화면 개선안을 검토했지만 교차 증정·조건 중첩 등 예외와 전체 인입 규모를 함께 봤을 때 시스템 변경보다 운영 기준 정리가 현실적이었습니다. 초회 문의에서는 부족한 증정품을 먼저 제공한 뒤 프로모션 조건을 안내하고, 재문의·추가 검토가 필요한 조건을 별도로 구분했습니다.

173건 → 143건(약 82%) 동일 유형VOC 분석 결과를 근거로 ‘제품을 고칠지, 운영 기준으로 풀지’까지 판단한 사례입니다.
실제 프로모션 고객 화면을 바탕으로 오인 지점을 검토했습니다.
CASE 03

3PL 전환 1,928건 → 우선순위 + 반복 등록 자동화

✕

CONTEXT

3PL 전환 초기 재배송 1,151건과 취소 777건, 총 1,928건의 후속 처리가 필요했습니다. 모든 건을 같은 순서로 처리하면 도착 약속과 재고 리스크가 큰 재배송이 늦어질 수 있었습니다.

OPERATING DESIGN

도착 일정·재고·고객 요청 기한을 기준으로 재배송과 취소를 분리하고 재배송을 먼저 처리했습니다. 동시에 반복 등록이 병목이어서 Claude를 코딩 보조로 Chrome Extension을 구현했습니다.

BACKOFFICE IMPROVEMENT

재배송을 접수하려면 원래 건의 반품·회수 정보를 샵어드민에 함께 등록해야 했습니다. 사유·귀책·회수·도착일 등 정형 입력을 단축키 한 번으로 채우도록 해 등록 동선을 7단계→1단계로 줄였습니다. 자동화는 1,928건 전체가 아니라 재배송 1,151건의 반복 등록에 적용했고, 이후 일상 미출·반품 업무에도 재사용했습니다.

1,928건 우선순위화 · 재배송 입력 7→1단계 · 필요 인력 3명→2명 재산정고객 영향과 내부 처리 효율을 동시에 본 운영 개선 사례입니다.
실제 대량 후속 처리 과정의 일부입니다.
재배송 접수 과정에서 필요한 샵어드민 반품·회수 항목을 자동 입력한 실제 화면입니다.

PROOF OF CONCEPT · 환불계좌 사전검증

온라인 환불계좌 오류로 고객 재확인·지출요청 수정·재이체가 반복되는 문제를 확인하고, Popbill 예금주조회 API를 활용한 계좌 사전검증 도구를 제작·테스트했습니다. 환불 파일을 업로드하면 은행·계좌번호·예금주 일치 여부를 일괄 확인하도록 구성하고 조회비용과 처리량까지 산정해 적용을 제안했으나, 당시 처리 건수가 적어 추가 비용 대비 효용을 고려해 실제 배포는 보류했습니다.

ADOPTION

도구를 만드는 데서 끝내지 않고 Notion ‘자동화’ 페이지에 설치 방법, 사용 순서, 자동 입력 항목, 예외 조건과 FAQ를 정리했습니다. 실제 사용 중 운영 기준이 바뀌면 로직과 가이드를 함께 수정했습니다.

운영 적용 3종 + 계좌 사전검증 API 테스트대규모 시스템 개발 없이 고객센터의 반복 동선을 줄였고, 비용 대비 효용이 맞지 않는 건은 만들었더라도 배포하지 않는 기준으로 판단했습니다.
사내에 공유한 /담당자 조회 기능 배포 안내입니다. 이름·채널 정보는 가렸습니다.
상품명 일부만 입력해도 담당 MD와 상품코드를 함께 확인할 수 있는 실제 조회 결과입니다.
