CASE 01

반복 운영 업무 자동화 및 처리 상태 가시화

✕

Problem

반복 입력·조회·공유 업무가 수작업 중심으로 운영되어 처리량이 늘어날수록 누락과 지연이 발생할 가능성이 커졌습니다. 진행 현황도 담당자 외에는 보이지 않아 대량 이슈 발생 시 처리 상태를 빠르게 파악하기 어려웠습니다.

What I Did

A
Chrome Extension 기반 반복 입력 자동화

생성형 AI의 도움을 받아 Chrome Extension을 구현해 AS·재배송·반품 등록 처리 동선을 7단계에서 1단계 수준으로 줄였습니다. 귀책 판단·예외 케이스처럼 비용에 영향을 주는 구간은 담당자가 직접 확인하도록 남겼습니다.

B
Slack API 기반 담당자 조회 자동화

Slack API와 Apps Script로 /담당자 슬래시 커맨드를 구축해 상품코드·담당 MD를 즉시 조회할 수 있도록 했습니다. 매번 스프레드시트를 열어 찾던 과정을 없앴습니다.

C
Zapier + Google Sheets 기반 처리 현황 가시화

반복 커뮤니케이션 기록을 정리하고, 처리 현황을 팀 내에서 실시간으로 확인할 수 있는 구조를 만들었습니다. 대량 이슈 발생 시 누가 어떤 건을 담당하는지 한눈에 파악할 수 있었습니다.

CASE 02

고객 문의/VOC 구조화 및 담당 부서 이관 기준 설계

✕

Problem

환불·교환처럼 고객이 원하는 조치가 자유 텍스트 문의 안에 섞여 있어, 고객 의도를 다시 확인해야 하는 구조였습니다. 의사 확인 없이 임의로 처리할 경우 분쟁 리스크가 있었고, 재확인 왕복이 반복됐습니다.

What I Did

A
고객 의도 유형 분류 및 선택 구조 설계

고객 문의를 "환불 희망", "교환 희망", "재배송 희망", "확인 요청" 등 의도 기준으로 나누고, 1:1 문의 입력 단계에서 선택값으로 구분할 수 있도록 구조 개선안을 설계했습니다.

B
기존 CRM 필드 활용 · 개발 범위 최소화

답변 작성일과 중복되는 영역을 '해결방법' 필드로 대체하는 방향을 제안해, 별도 개발 범위를 늘리지 않고 구조를 바꿀 수 있는 지점을 찾았습니다. 해당 값이 CRM의 해결방법 필드로 노출되도록 연결했습니다.

C
문의 유형별 담당 부서 이관 기준 정리

채널톡·CRM·게시판으로 들어오는 문의를 유형별로 확인하고, MD·물류·재무·개발 등 담당 부서로 정확히 연결되도록 이관 기준을 정리해 지원 인력 누구나 같은 기준으로 이관할 수 있도록 했습니다.

재확인 왕복 감소 · 담당 부서 연결 기준 명확화
자유 텍스트 → 의도 기반 선택값 · 임의 처리 리스크 감소
실제 화면
GOWID 연결

고위드 고객사 문의도 SaaS, 카드, IT기기, 비용 절감, 파트너 연결 등으로 나뉠 수 있어 초기 분류 기준이 중요합니다. 문의가 들어오는 시점에 의도와 처리 유형을 구분하면 이슈 접수 → 분류 → 대응 사이클을 빠르게 가져갈 수 있습니다.

Insight

응대 단계에서 발생하는 재확인 비용은 대부분 입력 단계의 구조 문제에서 시작됩니다. 큰 개발 변경 없이 기존 필드를 다르게 활용하는 방식만으로도 운영 비용을 빠르게 줄일 수 있습니다.

CASE 03

외부 파트너 사고·정산 기준 재정렬

✕

Problem

택배·물류 사고 발생 시 택배사, 물류사, 본사 간 증빙 요건과 비용 반영 기준이 달라 배상 처리가 지연되거나 회수로 이어지지 못하는 경우가 많았습니다. 물류 파트너 전환 이후에는 파트너 귀책 가능성이 있는 사고가 반복됐지만, 이를 정산 비용에 반영할 기준이 정해져 있지 않았습니다.

What I Did

A
원문 근거 기반 사고·증빙 기준 재정리

택배 표준약관과 실제 사고 접수 흐름을 기준으로, 사고 접수 기록과 현장에서 확보 가능한 외부 파손·오염 증빙을 기준으로 처리할 수 있도록 논점을 정리했습니다. 이를 통해 증빙 병목 없이 배상 처리로 이어질 수 있는 흐름을 만들었습니다.

B
물류 계약서 기준으로 파트너 귀책 비용 차감 기준 정리

물류 계약서 원문을 기준으로, 회사가 먼저 처리한 환불액·재배송비·CS 보상 비용을 익월 물류비 정산에서 차감 반영할 수 있는 기준을 정리했습니다. 외부 3PL 물류 파트너의 온라인 피해현황을 월별로 집계하고, 계약서 조항 기준으로 피해 유형·차감 예정액·조정 가능 항목을 정리해 정산 협의 자료로 관리했습니다. 확정액을 단순 수용하지 않고 확인 필요 사항을 함께 표시해 재검토 가능한 구조로 만들었습니다.

GOWID 연결

고위드도 SaaS·IT기기·제휴 파트너와 조건, 비용, 고객사 요청이 얽히는 구조입니다. 확인된 사실, 근거 규정, 증빙 기준, 책임 주체를 분리해야 같은 유형의 이슈를 반복 가능한 기준으로 처리할 수 있습니다.

Insight

운영 리스크가 생겼을 때 감정적 협의나 관행에 기대면 같은 문제가 반복됩니다. 원문 기준, 증빙 기준, 책임 주체, 정산 기준을 나눠 반복 가능한 판단 구조를 만들면 — 파트너가 바뀌어도, 사고 유형이 달라져도 — 같은 흐름으로 처리할 수 있습니다.

CASE 04

반복 VOC 기반 안내 구조 개선

✕

Problem

배송 가능 요일이 다른 상품이 함께 담기면 주문이 차단됐지만, 고객에게는 기존 품절형 메시지만 노출되어 실제 원인을 알기 어려웠습니다. 동일한 문의가 일 6~10건 반복됐습니다. 핵심 문제는 주문이 막히는 시점에 실제 차단 사유를 보여주지 못하는 화면 구조였습니다.

What I Did

A
반복 VOC 원인 재정의

문제를 단순 품절 문의가 아니라, 차단 사유가 화면에 드러나지 않는 안내 구조 문제로 재정의했습니다.

B
개발 제약을 고려한 최소 개선안 제안

차단 로직 전체를 바꾸는 것은 영향 범위가 컸기 때문에, 장바구니 단계에서 상품별 배송 가능 요일을 subtext로 안내하는 방식을 제안했습니다. 유사한 배송 제약 상품에도 재사용할 수 있도록 라벨 구조로 정리했습니다.

C
개발팀 협의 및 유사 케이스 확장

반복 문의 데이터와 실제 고객 혼선 지점을 함께 공유해 개발팀에 개선안을 전달했고, 제안은 당일 반영되었습니다. 이후 유사한 배송 제약 상품에도 같은 안내 구조를 확장 적용했습니다.
