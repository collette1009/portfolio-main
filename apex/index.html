CASE 01

반복 운영 업무 자동화 및 처리 상태 가시화

✕

Problem

상품 담당자 조회, 결품 고객 안내, AS 처리, 재배송·반품 입력 등 반복 업무가 수작업 중심으로 운영되어 처리 건수가 늘어날수록 누락과 지연이 발생할 가능성이 커졌습니다. 또한 진행 현황이 담당자 외에는 보이지 않아 대량 이슈 발생 시 처리 상태를 빠르게 파악하기 어려웠습니다.

What I Did

A
Chrome Extension 기반 반복 입력 자동화

생성형 AI의 도움을 받아 Chrome Extension을 구현해 반품·AS 등록 처리 동선을 7단계에서 1단계 수준으로 줄였습니다. 귀책 판단·예외 케이스처럼 비용에 영향을 주는 구간은 담당자가 직접 확인하도록 남겼습니다. 처음에는 대량 배송 지연·미출고 이슈 대응용으로 만들었지만, 이후 상시 발생하는 미출고·AS·재배송 처리에도 매일 동일한 구조를 그대로 적용하고 있습니다. 일회성 대응이 아니라 반복 운영 구조로 정착한 사례입니다.

B
Slack API 기반 내부 조회 구조 구축

Slack API와 Apps Script로 /담당자 슬래시 커맨드를 구축해 담당 MD·상품코드를 즉시 조회할 수 있도록 했습니다. 매번 스프레드시트를 열어 찾던 과정을 없앴습니다.

C
Zapier + Google Sheets 기반 처리 현황 가시화

Zapier와 Google Sheets로 반복 커뮤니케이션 기록을 정리하고, 처리 현황을 팀 내에서 실시간으로 확인할 수 있는 구조를 만들었습니다. 대량 이슈 발생 시 누가 어떤 건을 담당하는지 한눈에 파악할 수 있었습니다.

APEX 연결

APEX의 회차별 응시자 안내, 이슈 접수, 처리 현황 관리처럼 반복되는 운영 사이클에서도 같은 방식으로 누락 방지, 상태 가시화, 미처리 식별 구조를 적용할 수 있습니다. 자동화는 속도보다 중복·누락 방지와 처리 현황의 가시화가 목적입니다.

CASE 02

조직 공백 상황에서의 운영 기준 재정비

✕

Problem

회생 절차와 조직 변동으로 기존 운영 인력이 순차적으로 이탈하면서, 타부서 지원 인력이 CS 응대 업무에 투입되어야 하는 상황이었습니다. 기존 문서와 실제 처리 기준이 분산되어 있어 사람마다 판단이 달라질 가능성이 있었고, 물류 파트너 전환과 대량 지연·미출고 이슈가 겹쳐 상황이 복합적으로 얽혀 있었습니다.

What I Did

A
이슈 유형별 처리 기준 및 FAQ 재정리

배송 지연, 미출고, 환불·교환, 품질 민감 이슈별로 처리 기준과 FAQ를 재정리했습니다. 생성형 AI로 초안을 작성하고 실제 정책 기준에 맞게 금지어·확정 표현·책임 주체 표현을 정제했습니다.

B
답변 검수 및 에스컬레이션 기준 문서화

지원 인력의 답변을 직접 검수하면서 CS 처리 가능 범위와 타부서 판단 필요 범위를 구분한 에스컬레이션 기준을 정리했습니다. 같은 기준으로 피드백이 가능하도록 "상황 요약 → 위험 포인트 → 권장 문구 → 조치" 순서로 구조화했습니다.

C
신규·지원 인력 온보딩 가이드 제작

이슈 유형별 확인 순서, 쓰지 않아야 할 표현, 확인 주체를 정리한 온보딩 가이드를 제작했습니다. 담당자가 바뀌어도 같은 기준으로 운영이 이어질 수 있도록 문서로 남겼습니다.

SOP · 에스컬레이션 기준 · 온보딩 가이드 수립
개인 숙련도 의존 → 기준 문서 기반 운영 · 지원 인력도 같은 기준으로 응대 가능
보조 사례 · 민감 이슈 대응 기준 정렬
확인된 사실 · 안내 가능 범위 · 에스컬레이션 기준을 나누어 처리 품질 관리

문제 과거 조치가 완료된 품질 이슈가 외부 채널에서 다시 언급되면서, 매장과 고객 대응 기준이 필요한 상황이 발생했습니다. 동시에 별도의 내부 이슈와 혼동될 가능성이 있어, 현장에서 불필요한 정보를 먼저 언급할 경우 고객 불안과 리스크가 커질 수 있었습니다.

수행 고객에게 안내 가능한 확인 사실과, 내부 확인이 필요한 사항을 구분했습니다. 매장에는 "과거 발생했으나 조치가 완료된 건"임을 중심으로 안내하도록 기준을 정리했고, 고객이 별도 이슈를 직접 문의하는 경우에만 짧고 일관된 문구로 안내하도록 가이드를 제시했습니다. 이후 경영진 확인을 거쳐 현장 대응 방향을 정렬했습니다.

결과 매장별로 다른 답변이 나가는 것을 방지하고, 고객 불안을 키우지 않으면서도 필요한 사실은 안내할 수 있는 대응 기준을 마련했습니다. 민감 이슈를 감정적으로 대응하지 않고, 사실관계·공개 범위·에스컬레이션 기준으로 나누어 처리했습니다.

APEX 연결

시험 운영 초기에 매뉴얼이 부족하거나 담당자가 교체되는 상황에서도 운영 기준을 세울 수 있습니다. 또한 시험 중 이슈, 결과 이의제기, 보안 이슈가 발생했을 때 모든 정보를 한 번에 공개하는 것이 아니라, 확인된 사실과 안내 가능한 범위, 내부 확인이 필요한 범위를 구분해야 응시자 신뢰를 지킬 수 있다고 생각합니다.

Insight

개인이 더 빨리 처리하는 방법을 찾는 대신, 다른 사람도 같은 기준으로 따라올 수 있도록 기준 자체를 문서와 구조로 만들었습니다. 그래서 지원 인력이나 담당자가 바뀌어도 운영이 같은 기준으로 이어질 수 있는 형태로 남겼습니다.

CASE 03

✕

Problem

배송 가능 요일이 다른 상품이 함께 담기면 주문이 차단됐지만, 고객에게는 기존 품절형 메시지만 노출되어 실제 원인을 알기 어려웠습니다. 고객 입장에서는 상품이 품절됐거나 시스템 오류가 난 것처럼 보였고, 동일한 문의가 일 6~10건 반복됐습니다. 핵심 문제는 주문이 막히는 시점에 실제 차단 사유를 보여주지 못하는 화면 구조였습니다.

What I Did

A
반복 VOC 원인 재정의

문의 내용을 확인해보니 고객은 배송 정책 자체보다 "왜 지금 주문이 안 되는지"를 이해하지 못하고 있었습니다. 문제를 단순 품절 문의가 아니라, 차단 사유가 화면에 드러나지 않는 안내 구조 문제로 재정의했습니다.

B
개발 제약을 고려한 최소 개선안 제안

차단 로직 전체를 바꾸는 것은 영향 범위가 컸기 때문에, 장바구니 단계에서 상품별 배송 가능 요일을 subtext로 안내하는 방식을 제안했습니다. 특정 상품에만 적용되는 문구가 아니라, 유사한 배송 제약 상품에도 재사용할 수 있도록 라벨 구조로 정리했습니다.

C
개발팀 협의 및 유사 케이스 확장

반복 문의 데이터와 실제 고객 혼선 지점을 함께 공유해 개발팀에 개선안을 전달했고, 제안은 당일 반영되었습니다. 이후 유사한 배송 제약 상품에도 같은 안내 구조를 확장 적용했습니다.

APEX에서도 응시 자격, 시험 환경, 접수 상태, 결제, 결과 확인처럼 사용자가 막히는 지점이 생길 수 있습니다. 이때 전체 시스템을 바로 바꾸기 어렵더라도, 막히는 시점에 원인과 다음 행동을 명확히 보여주면 반복 문의와 불신을 줄일 수 있습니다. 이 케이스는 시스템 제약을 고객이 이해 가능한 안내 구조로 바꾼 경험입니다.

Insight

같은 정보를 충분히 안내하지 않으면 고객은 시스템 오류로 받아들입니다. 차단 로직 전체를 바꾸기 어려운 상황에서도, 막히는 시점에 이유를 먼저 보여주면 혼선을 줄일 수 있습니다. 개발 제약이 있더라도 안내 구조만 바꿔도 반복 문의를 빠르게 줄일 수 있습니다.

CASE 04

고객 의도 기반 문의 입력 구조 개선 — 자유 텍스트를 처리 가능한 선택값으로 전환

✕

Problem

환불·교환처럼 고객이 원하는 조치가 별도 선택값으로 분리되어 있지 않아, 자유 텍스트 안에서 고객 의도를 다시 확인해야 하는 구조였습니다. 의사 확인 없이 임의로 처리할 경우 분쟁 리스크가 있었고, 재확인 왕복이 반복됐습니다.

What I Did

A
고객 의도 유형 분류 및 선택 구조 설계

고객 문의를 "환불 희망", "교환 희망", "재배송 희망", "확인 요청" 등 의도 기준으로 나누고, 1:1 문의 입력 단계에서 선택값으로 구분할 수 있도록 구조 개선안을 설계했습니다.

B
기존 CRM 필드 활용 · 개발 범위 최소화

답변 작성일과 중복되는 영역을 '해결방법' 필드로 대체하는 방향을 제안해, 별도 개발 범위를 늘리지 않고 구조를 바꿀 수 있는 지점을 찾았습니다. 해당 값이 CRM의 해결방법 필드로 노출되도록 연결했습니다.

재확인 왕복 감소 · 처리 기준 명확화
자유 텍스트 → 의도 기반 선택값 · CRM 필드 연결 · 개발 범위 최소화
실제 화면
APEX 연결

시험 운영에서도 "문의", "오류 신고", "응시 환경 문제", "결과 이의제기"가 자유 텍스트로만 들어오면 우선순위 판단이 늦어질 수 있습니다. 처음부터 의도와 처리 유형을 나누는 입력 구조가 있으면 이슈 접수 → 분류 → 대응 사이클을 훨씬 빠르게 가져갈 수 있습니다.

Insight

응대 단계에서 발생하는 재확인 비용은 대부분 입력 단계의 구조 문제에서 시작됩니다. 큰 개발 변경 없이 기존 필드를 다르게 활용하는 방식만으로도 운영 비용을 빠르게 줄일 수 있습니다.

CASE 05

외부 파트너 사고·배상 기준 재정렬 — 원문 근거로 증빙·정산 기준 구조화

✕

Problem

택배·물류 사고 발생 시 택배사, 물류사, 본사 간 증빙 요건과 비용 반영 기준이 달라 배상 처리가 지연되거나 회수로 이어지지 못하는 경우가 많았습니다. 파손 스캔이나 운송 중 훼손이 확인된 건도 회수, 송장 사진, 외부 박스 사진, 내품 사진 등 증빙 요건을 모두 충족하지 못하면 배상 처리로 이어지기 어려웠습니다. 물류 파트너 전환 이후에는 출고 누락·포장 불량·파손 등 파트너 귀책 가능성이 있는 사고가 반복됐지만, 이를 정산 비용에 반영할 기준이 정해져 있지 않았습니다.

What I Did

A
원문 근거 기반 사고·증빙·정산 기준 재정리

택배 표준약관과 실제 사고 접수 흐름을 기준으로, 택배사 시스템상 사고가 확인된 건은 회수·사진 3종을 일괄 요구하기보다 사고 접수 기록과 현장에서 확보 가능한 외부 파손·오염 증빙을 기준으로 처리할 수 있도록 논점을 정리했습니다. 이를 통해 증빙 병목 없이 배상 처리로 이어질 수 있는 흐름을 만들었습니다.

B
물류 계약서 기준으로 파트너 귀책 비용 차감 반영

물류 계약서 원문을 기준으로, 초록마을이 먼저 처리한 환불액·재배송비·CS 보상 비용을 익월 물류비 정산에서 차감 반영할 수 있는 기준을 정리했습니다. 파손·누락·지연 이슈를 비용 유형별로 나누어 정산 협의 자료로 정리하고, 파트너가 제시한 확정액을 그대로 수용하지 않고 재검토 후 재정산을 요청했습니다.

C
사고 유형·증빙·정산 기준을 같은 언어로 정렬

사고 유형, 증빙 기준, 비용 반영 기준을 유관 리더와 파트너가 같은 기준으로 이해하고 처리할 수 있도록 정리했습니다. 부가적으로, 동일 사고가 고객·매장·택배사·본사로 중복 인입되지 않도록 안내 기준을 정리해 사고 확인과 보상 판단 흐름이 분리되도록 했습니다.

원문 근거 기반 증빙 기준 재정리 · 파트너 귀책 비용 정산 반영 · 사고 유형·증빙·정산 기준 정렬
APEX 연결

APEX에서도 시험 운영 중 장애, 부정행위 의심, 결과 이의제기, 외부 파트너 이슈가 발생했을 때 감정적 판단이나 관행에 의존하면 신뢰가 흔들릴 수 있습니다. 확인된 사실, 근거 규정, 증빙 기준, 책임 주체, 후속 처리 기준을 분리해야 같은 유형의 이슈를 반복 가능한 기준으로 처리할 수 있다고 생각합니다. 이 케이스는 시험 운영 경험 자체는 아니지만, 운영 리스크를 원문과 증빙 기준으로 구조화해 신뢰 가능한 처리 흐름으로 바꾼 경험입니다.

Insight

운영 리스크가 생겼을 때 감정적 협의나 관행에 기대면 같은 문제가 반복됩니다. 원문 기준, 증빙 기준, 책임 주체, 정산 기준을 나눠 반복 가능한 판단 구조를 만들면 — 파트너가 바뀌어도, 사고 유형이 달라져도 — 같은 흐름으로 처리할 수 있습니다.
