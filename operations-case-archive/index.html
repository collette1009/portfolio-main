How to use

이력서

포트폴리오

면접

첨부 화면은 개인 이름·연락처·주문정보가 식별되지 않도록 가려진 자료만 사용했습니다.

CASE 01 · 대량 예외 운영1,928건 · 7→1단계 · 3→2명

물류 전환기 1,928건을 우선순위로 나누고, 자동화 후 필요한 인력까지 다시 계산했습니다.

재배송 1,151건과 취소 777건이 동시에 쌓인 상황을 단순 분담이 아니라 처리 기한·고객 영향·재고 리스크 기준으로 재구성했습니다.

상세 보기
문제

외부 물류 운영사 전환 직후 재배송과 취소 대상이 동시에 발생해, 같은 순서로 처리하면 고객 약속과 재고 리스크가 커지는 상황이었습니다.

판단

취소는 요청 접수 기한 이후 일괄 처리할 수 있지만 재배송은 늦어질수록 고객 영향이 커졌습니다. 따라서 처리량이 아니라 영향도와 마감 시점으로 순서를 나눠야 한다고 판단했습니다.

실행

재배송을 먼저 처리하고, 관리자 화면의 정형 입력은 Chrome Extension으로 자동화했습니다. 자동화 적용 후 처리 속도를 기준으로 지원 인력을 3명에서 2명으로 재산정했습니다.

결과

총 1,928건을 유형과 처리 시점으로 나눠 운영했고, 반복 등록 동선을 7단계에서 1단계로 줄였습니다.

이력서용 1줄 · 물류 전환기 1,928건의 예외 업무를 고객 영향·기한 기준으로 우선순위화하고, 관리자 입력을 7→1단계로 자동화해 지원 인력을 3→2명으로 재산정
Product Operations커머스 운영운영 효율화리소스 산정
CASE 02 · 배송 제약 UX문의 5→0건

기술 제약을 확인한 뒤 요구사항을 최소 기능으로 줄여 배송일 충돌 문제를 해결했습니다.

모든 경우의 수를 설명하는 화면 대신, 충돌이 발생한 순간에만 이유를 노출하는 방식으로 범위를 좁혔습니다.

상세 보기
문제

출고 요일이 다른 상품을 함께 담으면 배송 가능한 날짜가 없어 주문이 막혔지만, 고객은 이유를 알 수 없어 반복 문의가 발생했습니다.

판단

개발팀으로부터 모든 조합과 예외를 화면에서 설명하기 어렵다는 제약을 확인했습니다. 전체 구조를 바꾸기보다 충돌 상황에만 최소한의 원인을 보여주는 편이 실행 가능하다고 판단했습니다.

실행

‘같이 배송 가능한 날짜가 없습니다’ 수준의 안내와 필요 시 FAQ 연결로 요구사항을 재정의하고, 장바구니에서 상품별 제한 이유가 보이도록 협의했습니다.

결과

반영 이후 동일 유형 문의가 5건에서 0건으로 감소했습니다.

이력서용 1줄 · 배송일 충돌 문의를 재현하고 기술 제약에 맞춰 요구사항을 최소 기능으로 재정의해 동일 유형 문의 5→0건 개선

CASE 03 · 프로모션 운영VOC 173건 · 82.1%

1+1 VOC 173건을 분석하고, 개발보다 저비용 운영정책이 적합한 문제를 구분했습니다.

UI 개발을 무조건 밀지 않고 원인 규모·예외 복잡도·비용을 비교해 초회 예외와 재인입 기준을 나눴습니다.

상세 보기
문제

1+1 혜택 미적용 문의가 반복됐지만, 고객이 실제로 어떤 조건에서 오인하는지 근거가 없어 대응이 사람마다 달라질 수 있었습니다.

판단

PC·모바일 구조와 예외 케이스를 모두 바꾸는 개발 비용에 비해 문의 절대량이 제한적이었습니다. 즉시 개발하기보다 운영정책으로 통제하며 추이를 보는 편이 타당하다고 판단했습니다.

실행

173건을 전수 분류해 문구 미인지 142건(82.1%), 정책 기준 혼동 12건, 홀수 수량 알림 부재 19건으로 나눴습니다. 초회 예외 처리와 재인입 시 정책 안내·종결 기준을 분리했습니다.

결과

프로모션 비용이 걸린 예외 처리를 동일 기준으로 판단할 수 있게 했고, 추후 재발 규모에 따라 UI 검토를 재개할 수 있는 근거를 남겼습니다.

이력서용 1줄 · 1+1 VOC 173건을 전수 분석해 82.1%의 주원인을 확인하고, 개발 복잡도와 문의 규모를 비교해 초회 예외·재인입 운영 기준 수립
Business Operations프로모션 운영데이터 기반 판단정책 설계
CASE 04 · 파트너 정책 협의배상 회수액 약 14.7배

‘회수 없이는 보상 불가’라는 파트너 정책을 자체 약관 근거로 다시 협의했습니다.

개별 예외 요청이 막히자 고객 편의가 아니라 파트너의 송화인 통보·사고 조치 의무 이행 문제로 협상 기준을 바꿨습니다.

상세 보기
문제

파손 사고 접수에 실물 회수와 사진 3종이 필요해, 이미 사고를 겪은 고객이 재포장·보관·추가 입증을 해야 했고 중도 포기 건은 배상으로 이어지지 않았습니다.

판단

‘거래처별 예외 적용 불가’라는 답변에 같은 편의 논리로 요청을 반복해서는 기준을 바꾸기 어렵다고 판단했습니다.

실행

택배 표준약관의 송화인 통보 의무와 사고 발생 시 조치 의무를 확인해, 파손 인지 후 공유 누락과 전 영업소 지침을 재협의 대상으로 전환했습니다.

결과

택배사는 내부 검토 후 실물 회수 없이 사고를 접수하고 사진으로 대체하는 안을 제안했습니다. 비교 월 배상 회수액은 50만 원대에서 약 744만 원으로 확대됐습니다.

이력서용 1줄 · 택배사의 ‘회수 없이는 보상 불가’ 정책을 자체 약관의 통보·조치 의무로 재협의해 실물 회수 없는 사고 접수안 도출 및 비교 월 배상 회수액 약 14.7배 확대
파트너 운영정책 협상리스크 관리비용 회수

※ 약관이 ‘회수 없는 보상’을 직접 규정했다고 해석하지 않고, 약관을 협상 논점 전환의 근거로 사용한 사실만 기재했습니다.

CASE 05 · 이상 주문 통제기준 검증·모니터링

리셀러·우회 발주를 감이 아니라 주문 패턴과 정책 기준으로 판단했습니다.

주문자·수령자 불일치, 대량 구매, 배송지 패턴과 기존 등록 근거를 다시 대조했습니다.

상세 보기
문제

리셀러 등록 사유가 불명확한 계정이 있었고, 미수 매장이 소비자 채널로 우회 주문하면 제재 실효성·형평성·재고 추적이 흔들릴 수 있었습니다.

판단

단일 대량 주문만으로 차단하면 정상 고객을 오판할 수 있어 여러 패턴과 공식 기준을 함께 봐야 했습니다.

실행

기존 판단 기준을 재확인하고 주문자·수령자 불일치, 구매량, 반복 배송지 등 의심 패턴을 정리했습니다. 정책 우회 가능성이 있는 주문은 모니터링하고 기준에 따라 기주문 취소까지 운영했습니다.

결과

‘이상해 보이는 주문’이 아니라 검토 가능한 기준으로 주문 리스크를 관리할 수 있게 했습니다.

이력서용 1줄 · 리셀러·우회 발주 의심 주문을 주문자/수령자·구매량·배송지 패턴과 공식 기준으로 재검증하고 모니터링·주문 통제 체계 운영
커머스 운영Fraud/Risk Ops정책 우회 탐지
CASE 06 · 상품 운영 기준사전 예방

출고 제약을 사후 CS가 아니라 상품 등록 단계의 운영 기준으로 옮겼습니다.

특정 요일 출고·발주요일 변경 상품을 EC가 주의상품으로 태깅하도록 제안했습니다.

상세 보기
문제

출고 가능 요일이 제한되거나 발주요일이 바뀐 상품은 고객이 일반 상품과 함께 주문한 뒤에야 배송일 차이를 알게 됐습니다.

판단

문제가 발생한 뒤 CS가 설명하는 방식으로는 같은 문의가 반복됩니다. 상품 운영 단계에서 제약을 함께 전달해야 한다고 판단했습니다.

실행

신규 상품 등록이나 발주요일 변경 요청 시 EC가 주의상품 태깅까지 함께 요청하도록 운영 기준을 제안했습니다.

결과

배송 제약을 사후 문의가 아니라 상품 운영 단계에서 미리 관리하는 구조를 만들었습니다.

이력서용 1줄 · 특정 요일 출고·발주일 변경 상품을 EC 등록 단계에서 주의상품으로 태깅하도록 운영 기준을 제안해 배송일 혼선의 사전 예방 구조 설계
상품 운영커머스 운영프로세스 개선
CASE 07 · 오류 재현·개발 협업당일 수정

반복되던 송장 조회 오류를 재현·증빙해 개발팀이 수정 가능한 문제로 바꿨습니다.

운영 불편 제보에서 끝내지 않고 영상과 조건을 붙여 실제 원인 확인까지 후속 관리했습니다.

상세 보기
문제

관리자 주문상세에서 실제 운송장번호 확인에 반복 클릭이 필요했고, 일부 로젠 송장 추적은 아예 열리지 않았습니다.

판단

간헐적 불편이라는 설명만으로는 개발팀이 원인을 찾기 어려워 재현 조건과 실제 실패 화면이 필요했습니다.

실행

오류 상황을 재확인하고 영상 증빙과 함께 전달했습니다. 수정 이후에도 실제 조회 여부를 다시 확인했습니다.

결과

개발팀이 배송조회 요청값에 하이픈이 포함되는 문제를 확인해 프론트를 수정했고, 당일 정상 동작까지 확인했습니다.

이력서용 1줄 · 반복 배송조회 오류를 재현·영상 증빙해 개발팀에 전달하고, 요청값 형식 문제 확인과 당일 수정까지 후속 관리
Product OperationsQA개발 협업이슈 관리
CASE 08 · 내부 조회 도구Slack /담당자

공유 파일을 열어 찾던 상품 담당자를 Slack 명령어 한 번으로 조회하게 했습니다.

상품명·상품코드 부분검색, 미등록 예외 안내, 요청자 전용 응답까지 포함한 내부 도구입니다.

상세 보기
문제

상품 문의를 이관하려면 공유 파일을 열고 상품명이나 코드를 검색해 담당자를 찾아야 했습니다.

판단

반복 조회 규칙이 명확하고 결과 형식도 정형화돼 있어 내부 도구로 전환하기 적합했습니다.

실행

Slack API와 Apps Script를 이용해 `/담당자` 명령을 만들고 부분 상품명·상품코드 검색, 미등록 안내, 요청자에게만 보이는 응답을 구성했습니다.

결과

파일 열기–검색–코드 확인–담당자 확인의 동선을 한 번의 명령으로 줄이고 공통 조회 규칙을 만들었습니다.

이력서용 1줄 · Slack API·Apps Script 기반 `/담당자` 조회 도구를 구축해 공유 파일 검색 중심의 상품 담당자 확인 절차를 명령어 1회로 단축
운영 자동화Internal ToolSlack API
CASE 09 · 운영 시트 자동화중복·누락 방지

주문번호만 입력하면 수거 처리에 필요한 필드가 자동으로 채워지게 했습니다.

출고일·작업지시일·상품·고객 정보를 원장에서 가져오고 중복 주문은 한 건 기준으로 정리했습니다.

상세 보기
문제
